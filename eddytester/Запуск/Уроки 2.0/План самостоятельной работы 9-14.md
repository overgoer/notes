# 🕵️‍♂️ План самостоятельной работы (Уроки 9–14): Концепция «Детективных Дел»

> **Цель:** Сделать вторую (самостоятельную) половину курса захватывающей для студента, полезной («WOW-эффект»), но при этом **максимально простой в реализации для нас** (без написания сложного кода, используя готовую архитектуру Progress API).

---

## 🗺️ Новая структура уроков (Прогрессия «Детектива»)

### Урок 9. Инструктаж перед высадкой (Переходное видео)
*   **Концепт:** Короткое видео (5–7 минут). Эдди снимает «тренировочные колёса» и объясняет правила взрослой игры.
*   **Темы в видео:** 
    *   Как устроен самостоятельный аудит API.
    *   Твой «компас» (спецификация в Notion/Google Docs) и твой «чит-код» (V2).
    *   Как не бояться белого экрана и ошибок в Postman.
*   **Интерактив на платформе:** Теста нет. Только кнопка «Я готов начать расследование!», которая переводит студента к следующему шагу.

---

### Урок 10. Дело №1: «Первые подозреваемые» (GET /users & GET by ID)
*Студент впервые самостоятельно ищет баги, часть из которых он видел на экране в Уроках 5–8, а часть находит с нуля.*
*   **Сюжет:** «Твоё первое самостоятельное дело. База данных подозреваемых `GET /users` ведёт себя странно. Поговаривают, некоторые данные вообще невозможно найти, а система безопасности дырявая как решето».
*   **Что студент ищет сам (наши чекбоксы):**
    *   **GET /v1/api/users (все юзеры):**
        *   `g_content_type` — Content-Type возвращается как `text/plain` вместо `application/json` *(видел в видео)*.
        *   `g_status_case` — Фильтр по статусу чувствителен к регистру (`?status=Candidate` возвращает пустой список) *(видел в видео)*.
        *   `g_cache` — Публичное кэширование на 3 минуты (Cache-Control) *(видел в видео)*.
        *   `g_security` — Отсутствие заголовков безопасности `X-Content-Type-Options` и `X-Frame-Options` *(видел в видео)*.
        *   `g_cache_info` — Утечка служебного заголовка `X-Cache-Info` *(видел в видео)*.
        *   `g_empty_status` — Пустой статус `?status=` возвращает `200 OK` и `[]` вместо ошибки `400 Bad Request` — *новая улика!*
        *   `g_comma` — Запрос через запятую `?status=minor,candidate` молча игнорируется.
    *   **GET /v1/api/users/:id (конкретный юзер):**
        *   `u_not_found` — Запрос по несуществующему ID возвращает `200 OK {}` вместо `404 Not Found` — *новая улика!*
        *   `u_string_id` — Запрос со строковым ID (например, `/users/abc`) выдаёт ошибку базы данных (500) вместо цивилизованной `400 Bad Request` — *новая улика!*
*   **Инструменты в материалах:**
    *   `[📂 Подсказка: Как искать?]` ➔ Раскрывающийся блок: *"Попробуй запросить ID, которого точно нет в базе. Каким должен быть HTTP-статус ответа по спецификации? А что фактически возвращает V1?"*

### Урок 11. Дело №2: «Фальшивые документы» (POST /users)
*Учим ломать логику создания данных и проверять побочные эффекты в БД.*
*   **Сюжет:** «Разработчики утверждают, что закрыли дыры при создании новых профилей подозреваемых. Давай проверим, насколько они честны».
*   **Что студент ищет сам:**
    *   `p_name_special` — Имя `John123` (с цифрами) сохраняется без ошибок *(видел в видео)*.
    *   `p_age_66` — Не даёт создать пенсионера (66 лет) в V1 *(видел в видео)*.
    *   `p_age_string` — Позволяет передать возраст как строку в JSON-теле.
    *   `p_passes` — Создаётся по 2 пропуска на одного юзера вместо 1 — *работаем с БД!*
    *   `p_lowercase_code` — Префикс кода пропуска `scr_` строчный вместо `SCR-` — *проверка формата!*
*   **Инструменты в материалах:**
    *   `[📂 Подсказка: Как проверить БД?]` ➔ *"Открой DBeaver, сделай запрос `SELECT * FROM passes WHERE user_id = ...`. Посчитай количество строчек и посмотри на префикс кода!"*

### Урок 12. Дело №3: «Подмена личности» (PATCH /users/:id)
*Тестируем обновление данных. Самые частые баги реальных проектов.*
*   **Сюжет:** «Подозреваемый пытается изменить свои данные в базе. Нам нужно проверить, насколько защищён метод обновления».
*   **Что студент ищет сам:**
    *   `pa_partial_update` — По ТЗ PATCH требует отправки обоих полей (name + age), но V1 сохраняет даже если отправить только одно.
    *   `pa_string_age` — После обновления возраст `age` возвращается в кавычках (как строка `"25"` вместо числа `25`).
    *   `pa_missing_id` — Из ответа сервера полностью пропадает поле `id` обновлённого юзера.
*   **Инструменты в материалах:**
    *   `[📂 Подсказка: Как сломать PATCH?]` ➔ *"Попробуй убрать из тела запроса поле age и отправить только name. Сверь поведение V1 и V2."*

---

### Урок 13. Дело №4 (Экзамен): «Исчезновение без следа» (DELETE /users/:id)
*Главный WOW-момент курса. Драматургия лживого API.*
*   **Сюжет:** «Подозреваемый стирает свои следы. Сервер говорит, что всё удалено. Но так ли это на самом деле?»
*   **Что студент ищет сам:**
    *   `d_double_delete` — Повторное удаление возвращает `200 OK "Deleted"` вместо `404 Not Found`.
    *   `d_db_not_deleted` — Пользователь физически остаётся в таблице БД после удаления! *(Иллюзия удаления)*.
*   **Инструменты в материалах:**
    *   `[📂 Самая важная подсказка в твоей жизни]` ➔ *"Удали пользователя через DELETE в Postman. Получил 200 OK? А теперь иди в DBeaver и сделай SELECT * FROM users. Ты видишь его? Да, API нагло врёт. Тестировщик верит только базе данных!"*

## 🛠 Техническая реализация (Простота для нас):
1. **Фронтенд:** Если урок добавлен в `LESSON_MAP` и под ним создан пустой `<div class="test-section"></div>`, наш JS-код **автоматически** генерирует интерактивный чекбокс-лист, проверяет ответы на бэке, выводит попытки, подсвечивает ошибки и пересчитывает общий прогресс-бар в сайдбаре.
2. **Бэкенд:** Нам нужно только прописать JSON-структуру вопросов/чекбоксов в `LESSONS_CONFIG` в файле `progress.js`.

Всё, что нам нужно сделать — это написать красивый, вовлекающий текст заданий и подсказок в HTML-блоках уроков!
