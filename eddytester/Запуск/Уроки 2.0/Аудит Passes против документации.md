# Аудит Passes против документации — Passes Quest

> Сверка 5 методов screening passes с Google Docs (секции 6–10). Обсуждено с Эдди 23.08.
> Итог: баги зафиксированы, вносим правки: v2-код → бэк (LESSONS_CONFIG) → фронт (блоки) → дока. По одной правке, с проверкой v1 и v2.

---

## Итоговые списки багов и дистракторов

### 1. GET /v1/api/passes — список (6 чекбоксов)
**Баги:**
- limit и offset игнорируются — `?limit=2` вернёт все записи
- Даты без миллисекунд и Z (issued_at, expires_at, updated_at)
- Нет заголовков безопасности, Cache-Control: public

**Дистракторы:** «список не отсортирован» (ORDER BY есть) · «в ответе нет api_key» (есть) · «пагинация работает корректно» (наоборот — баг №1)

### 2. POST /v1/api/passes — создание (8 чекбоксов)
**Баги:**
- 60 часов вместо 1 часа
- Нет проверки user_id — можно создать для несуществующего/чужого (нет 404)
- Нет запрета для minor
- Нет запрета дубликата активного пропуска
- pass_code: `scr_` + нижний регистр вместо `SCR-` + заглавные

**Дистракторы:** «пустой user_id → 500» (400) · «создаёт 2 пропуска за раз» (1) · «статус pending» (active)

### 3. GET /v1/api/passes/user/:user_id (7 чекбоксов)
**Баги:**
- Игнорирует :user_id — возвращает пропуск не того кандидата
- Пустой случай: нет пропуска у запрошенного → вернёт чужой вместо {passes: []}
- Даты без миллисекунд и Z
- Нет заголовков безопасности, Cache-Control: public

**Дистракторы:** «нет пропусков → 404» (200 + []) · «не отсортирован» · «нет pass_code в ответе»

### 4. PATCH /v1/api/passes/:id (9 чекбоксов)
**Баги:**
- Любой статус принимается (banana)
- updated_at не обновляется
- Иммутабельные поля меняются (user_id, pass_code)
- Воскрешение просроченного по времени
- Лимит активных сломан (второй активный у кандидата)
- Нет заголовков безопасности, Cache-Control: public

**Дистракторы:** «несуществующий id → 500» (404) · «PATCH удаляет пропуск» · «в ответе нет id»

### 5. DELETE /v1/api/passes/:id (7 чекбоксов)
**Баги:**
- Нет фильтра api_key — можно удалить чужой пропуск
- 200 «Deleted» вместо 404 «Pass not found»
- Активный пропуск удаляется без ошибки (новое правило — см. правку доки)
- Нет заголовков безопасности, Cache-Control: public

**Дистракторы:** «несуществующий → 500» (200) · «тело пустое» (message есть) · «удалённый пропуск возвращается в ответе»

---

## Бизнес-логика отзыва (зафиксировано)

- Отзыв ≠ удаление: отозвать = PATCH → expired (запись в истории); удалить = только недействительный
- Машина состояний: active → expired (вручную или по времени) → delete; вручную отозванный можно вернуть в active, пока не истёк срок

## План имплементации (по шагам)

1. **v2 код:** DELETE /passes — запрет удаления активного (400 «Cannot delete an active screening pass») + Jest-тест
2. **Бэк:** 5 записей LESSONS_CONFIG (passes-list, passes-post, passes-by-user, passes-patch, passes-delete) — без testType (bug-hunt), correct[] по спискам выше
3. **Фронт:** блоки Passes Quest (l14–l18) + LESSON_MAP + отдельная секция с achievement «🎖 Настоящий тестировщик» (по концепту)
4. **Дока (по одной правке, филигранно):**
   - Секция 10: ограничение «нельзя удалить активный пропуск» + ошибка 400 «Cannot delete an active screening pass»
   - Секция 8: уточнить «какой пропуск возвращается при нескольких»; api_key в примере — привести к методу 6
5. **E2E:** прогнать Passes Quest браузером (как уроки 1–13), проверить счётчик
